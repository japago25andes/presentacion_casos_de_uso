Antes del diagrama: los requisitos

Un caso de uso no nace de la nada: nace de lo que el cliente necesita que el sistema haga.

Dos tipos de requisito

¿Qué hace el sistema… y qué tan bien lo hace?

RF · Requisito funcional

Describe QUÉ hace el sistema

Un servicio o función concreta: cómo responde el sistema a una entrada o a una acción del usuario.

  • El sistema permitirá al usuario iniciar sesión con usuario y contraseña.
  • El sistema calculará el impuesto de cada compra.
  • El sistema enviará un correo de confirmación tras cada pedido.
RNF · Requisito no funcional

Describe CÓMO debe comportarse

Cualidades y restricciones: rendimiento, seguridad, disponibilidad, usabilidad… Aplican a todo el sistema o a varias funciones.

  • El inicio de sesión debe responder en menos de 2 s.
  • Las contraseñas se almacenarán cifradas.
  • El sistema estará disponible el 99,5 % del tiempo.
Analogía del carro: «el carro frena» es funcional. «Frena de 100 a 0 km/h en menos de 40 m» es no funcional. Si el RNF no se cumple, la función existe… pero nadie la quiere usar.
Requisitos no funcionales en el SINU

Las familias más comunes de RNF

Rendimiento

La matrícula debe confirmarse en menos de 3 s con 5.000 estudiantes conectados.

Seguridad

Solo el docente titular puede registrar o modificar las notas de su grupo.

Disponibilidad

El portal debe funcionar 24/7 durante el calendario de matrículas.

Usabilidad

Un estudiante nuevo debe poder matricularse sin capacitación en menos de 10 min.

Compatibilidad

Debe funcionar en Chrome, Edge y Firefox, y en celulares.

Mantenibilidad

Agregar un nuevo programa académico no debe requerir cambiar el código.

Regla de oro: un requisito debe ser verificable. ✕ «El sistema debe ser rápido». ✓ «Debe responder en menos de 3 s con 5.000 usuarios concurrentes».
Actividad · 2 minutos

¿Funcional o no funcional?

1. El estudiante podrá descargar su certificado de notas en PDF.
Es un servicio que el usuario solicita: una función.
2. Toda consulta debe responder en menos de 2 segundos.
Rendimiento: dice qué tan bien, no qué.
3. El docente podrá registrar las notas de los tres cortes.
Acción concreta del docente sobre el sistema.
4. Las contraseñas se almacenarán cifradas.
Seguridad: restricción sobre cómo se guarda la información.
5. El sistema enviará un correo cuando se publique una nota.
Es un comportamiento observable del sistema.
6. La interfaz debe verse correctamente en celulares.
Compatibilidad / usabilidad.
7. El administrador generará el reporte de matriculados por programa.
Generar un reporte es una función, aunque el formato sea PDF.
8. Se hará copia de seguridad de la base de datos cada noche.
Debatible y válido discutirlo: suele tratarse como RNF de confiabilidad/recuperación.
Haz clic en la respuesta que elija el grupo.

La perspectiva

El guion de la película

No puedes construir una casa si no sabes quién vivirá en ella y qué hará en cada habitación.

El guion no explica cómo funciona la cámara: cuenta qué pasa en la escena, quién actúa y cómo termina.

Los casos de uso definen el valor que el sistema entrega al mundo exterior.
Definición

Un caso de uso es…

… una secuencia de acciones que realiza el sistema y que produce un resultado observable de valor para un actor en particular.

Basada en Jacobson, Booch y Rumbaugh, creadores de UML.

Secuencia de acciones

No es un clic aislado: es una conversación de varios pasos entre el actor y el sistema.

Que realiza el sistema

Describe cómo responde el software, no lo que el usuario hace fuera de él.

Resultado de valor

Al terminar, el actor obtiene algo concreto: una matrícula, un certificado, un pago.

Para un actor

Siempre hay alguien (o algo) que lo inicia y se beneficia de él.

El error típico de Software I

Lo que NO es… y lo que SÍ es

Lo que NO es

No es un diagrama de flujo.
No muestra el orden temporal paso a paso.
No incluye lógica de programación (if / else, bucles).
No describe pantallas, botones ni tablas de la base de datos.

Lo que SÍ es

Muestra QUÉ hace el sistema.
Muestra QUIÉN interactúa con él.
Muestra el VALOR o la meta que se alcanza.
Define el alcance: qué está dentro y qué está fuera.
¿Por qué le importa al cliente?

Contrato visual

«Esto es lo que te voy a construir.» El cliente no lee diagramas de clases, pero entiende sus procesos.

Estimación

A más casos de uso (y más complejos), más tiempo y costo.

Base para pruebas

Cada flujo se convierte en uno o varios casos de prueba.

Guía del equipo

Diseño, desarrollo y QA trabajan sobre la misma historia.

03

Anatomía del diagrama

Cuatro piezas, unas reglas para nombrarlas y una forma de heredar comportamiento.

Notación UML

Las cuatro piezas del diagrama

1 · Actor

Muñeco de palitos. El usuario o sistema externo que interactúa. Siempre fuera del sistema.

2 · Caso de uso

Óvalo con un verbo en infinitivo + objeto. Es la meta del actor.

3 · Límite del sistema

La caja con el nombre del sistema. Separa nuestro software del mundo exterior.

4 · Asociación

Línea continua que conecta al actor con los casos de uso en los que participa.

Rompiendo mitos

Un actor no siempre es una persona

Cualquier entidad externa que envíe o reciba información del sistema es un actor. El actor es un rol, no una persona: la misma persona puede ser Estudiante y Monitor.

Actores humanos

Estudiante, Docente, Coordinador académico, Cajero.

Sistemas externos

Pasarela de pagos PSE, API de la Registraduría, sistema financiero de la U.

El tiempo

Un proceso automático: cerrar el registro de notas al final de cada corte a las 23:59.

Actor principal: inicia el caso de uso para lograr su meta. Por convención se dibuja a la izquierda.
Actor secundario: el sistema le pide ayuda para cumplir la meta (ej. el sistema financiero). Se dibuja a la derecha.
Buenas prácticas

Cómo nombrar un caso de uso

Verbo en infinitivo + objeto (+ complemento)

Nombres correctos

Matricular asignatura
Registrar notas del corte
Pagar matrícula en línea
Generar certificado de estudios
Reservar sala de estudio

Nombres a evitar

«Matrícula» — sustantivo: no dice qué acción ocurre.
«Botón Guardar» — es interfaz, no una meta.
«Abrir la página de inicio» — navegación sin valor.
«Base de datos de notas» — es un componente.
«Gestionar todo el sistema» — demasiado amplio.
Granularidad

Ni muy grande, ni muy pequeño

Demasiado grande

Administrar universidad

Es un proceso de negocio completo. Se debe dividir en varios casos de uso.

Tamaño correcto

Matricular asignatura

Una persona, una sesión, una meta cumplida. El actor se va satisfecho.

Demasiado pequeño

Digitar código

Es solo un paso dentro de otro caso de uso. Va en la especificación.

Prueba de la meta

¿El actor podría irse satisfecho después de terminarlo? Si la respuesta es no, probablemente es un paso, no un caso de uso.

Prueba del jefe

Si tu jefe pregunta «¿qué hiciste hoy?» y respondes «digité un código», no tiene sentido. «Matriculé 5 asignaturas», sí.

Herencia en el diagrama

Generalización

Línea continua con triángulo hueco que apunta hacia el elemento general (el «padre»).

Entre actores

El hijo hereda todos los casos de uso del padre y puede tener los suyos. Estudiante y Docente pueden hacer todo lo que hace un Usuario.

Entre casos de uso

Varias formas de lograr la misma meta. «Pagar con PSE» y «Pagar en banco» son tipos de «Pagar matrícula».

Úsala solo cuando el hijo «es un tipo de» padre. Si dudas, no la uses.

El dolor de cabeza: include vs. extend

Cómo se relacionan los casos de uso entre sí dentro del sistema.

Dependencia obligatoria

«include»

El caso de uso base incorpora siempre el comportamiento del caso incluido. Sin él, el base no puede cumplir su objetivo.

  • Flecha punteada con la etiqueta «include».
  • Va desde el base hacia el incluido.
  • Sirve para reutilizar comportamiento común a varios casos de uso.
Frase guía: «Para Retirar dinero siempre debo Autenticar al cliente.»
Comprar en línea → «include» → Procesar pago
Matricular asignatura → «include» → Verificar deudas
Comportamiento opcional

«extend»

El caso de uso base funciona perfecto por sí solo. La extensión agrega comportamiento solo bajo cierta condición, en un punto de extensión del base.

  • Flecha punteada con la etiqueta «extend».
  • Va desde la extensión hacia el base. ¡Al revés que include!
  • El base no sabe que la extensión existe: solo declara dónde puede engancharse.
Frase guía: «Mientras Inicio sesión, a veces necesito Recuperar mi contraseña.»
Aplicar cupón → «extend» → Comprar en línea
Solicitar sobrecupo → «extend» → Matricular asignatura
Lado a lado

Include vs. extend

«include»«extend»
¿Ocurre siempre?Sí, cada vez que se ejecuta el base.No, solo si se cumple una condición.
¿El base funciona sin él?No: lo necesita para cumplir su meta.Sí: el base está completo por sí solo.
Dirección de la flechaBase ⇢ IncluidoExtensión ⇢ Base
¿Quién conoce a quién?El base conoce y «llama» al incluido.La extensión conoce al base; el base solo declara el punto de extensión.
Para qué sirveReutilizar o separar un bloque obligatorio.Agregar algo opcional o excepcional.
Frase guía«Para X siempre debo hacer Y.»«Mientras hago X, a veces hago Y.»
Truco para la flecha: la flecha sale de quien depende. Con include, el base depende del incluido. Con extend, la extensión depende del base (no tiene sentido sola).
Actividad · 3 minutos

¿Include o extend?

1. Para Retirar dinero el cajero siempre debe Validar el PIN.
Siempre ocurre y sin él no hay retiro → include.
2. Al Comprar boleta el cliente puede Aplicar un cupón si tiene uno.
Opcional y con condición → extend (Cupón ⇢ Comprar).
3. Matricular asignatura siempre debe Verificar prerrequisitos.
Obligatorio para lograr la meta → include.
4. Al Pagar pedido, si el usuario lo marca, se ejecuta Guardar tarjeta.
Depende de una decisión del usuario → extend.
5. En Realizar transferencia, si el monto supera $10 millones, se pide Validar código OTP.
Solo bajo una condición → extend.
6. Generar certificado y Generar factura usan siempre Firmar documento.
Comportamiento común y obligatorio → include (reutilización).
Pregunta clave: ¿ocurre siempre?
Evítalos en tu proyecto

Seis errores clásicos

Flecha de «extend» al revés
Nace en la extensión y apunta al caso base.
Casos de uso que son pantallas o botones
Nombra metas del actor: «Pagar matrícula», no «Pantalla de pago».
Convertirlo en diagrama de flujo
No encadenes include para mostrar el orden. El orden va en la especificación.
«Iniciar sesión» incluido en todo
Es una precondición de los demás. Modélalo una sola vez como caso de uso propio.
Actores dentro del sistema o conectados entre sí
Los actores van fuera de la caja y solo se conectan con casos de uso.
Extend para algo que siempre pasa
Si ocurre siempre es include. Si es opcional, extend.

El alternativo nace en el paso 5 y regresa al paso 4. La excepción nace en el paso 2 y termina sin lograr la meta.

Numeración: «5a» es la primera variante del paso 5, «5b» la segunda. Sus pasos internos son 5a1, 5a2… Las excepciones usan «e»: 2e.

Flujo básico

El «camino feliz»: pasos numerados en dos columnas, Actor | Sistema.

Flujos alternativos

Variantes que sí logran la meta por otro camino.

Excepciones

Errores o condiciones en las que la meta no se logra.

Postcondiciones

Lo que es cierto después: en caso de éxito y de fallo.

Relaciones

Includes usados y puntos de extensión declarados.

Requisitos especiales

Los RNF que aplican a este caso de uso.

Estilo de escritura

Ocho reglas para escribir buenos flujos

1

Sujeto + verbo en presente

«El estudiante selecciona…», «El sistema valida…». Siempre queda claro quién hace qué.

2

Una acción por paso

Si un paso tiene dos verbos importantes, divídelo en dos.

3

Sin detalles de interfaz

✕ «Hace clic en el botón azul» · ✓ «Confirma la matrícula»

4

Sin detalles técnicos

✕ «Ejecuta un SELECT» · ✓ «Consulta las asignaturas»

5

Sin if / else en el flujo básico

El camino feliz es lineal. Cada «si…» se convierte en un flujo alternativo o en una excepción.

6

Referencia el paso de origen

Cada alternativa dice dónde nace (5a) y a qué paso vuelve o si termina.

7

Termina con valor

El último paso deja al actor con su meta cumplida y algo observable: un comprobante, un mensaje.

8

Entre 3 y 10 pasos

Si el flujo básico pasa de 10 pasos, quizá son dos casos de uso. Si tiene 2, quizá es solo un paso.

CU-12 Devolver libro y su extensión CU-13

CU-12Devolver libro
Actor principalBibliotecario
DescripciónRegistra la devolución de un ejemplar prestado y actualiza su disponibilidad.
PrecondicionesEl bibliotecario inició sesión.
Flujo básico
  1. El bibliotecario escanea el código del ejemplar.
  2. El sistema muestra el préstamo: usuario y fecha límite.
  3. El bibliotecario confirma la devolución.
  4. El sistema registra la fecha y marca el ejemplar como «disponible».
Alternativos1a Código ilegible: el bibliotecario lo digita; vuelve al paso 2.
2a Punto de extensión «Retraso»: la fecha actual supera la fecha límite.
4a El ejemplar tiene reservas: queda «reservado» y se notifica al siguiente usuario.
Excepciones1e El ejemplar no tiene préstamo activo: el sistema lo informa y el caso de uso termina.
PostcondicionesEl préstamo queda cerrado y el ejemplar, disponible o reservado.
Extensión

CU-13 Calcular multa

Extiende a: CU-12, en el punto «Retraso».

Condición: fecha de devolución > fecha límite.

  1. El sistema calcula los días de retraso × tarifa diaria.
  2. El sistema registra la multa en la cuenta del usuario.
  3. El sistema bloquea nuevos préstamos hasta el pago.
  4. Regresa al paso 3 de CU-12.
El caso base solo nombra el punto de extensión. La extensión dice dónde y cuándo se engancha. Por eso la flecha va de CU-13 hacia CU-12.
Antes de entregar

Lista de chequeo de calidad

Cada caso de uso tiene un ID y un nombre con verbo en infinitivo.

Todo actor está fuera del sistema y conectado al menos a un caso de uso.

Las flechas de include van base ⇢ incluido y las de extend van extensión ⇢ base.

Las precondiciones son verificables y el caso de uso no las valida.

El flujo básico no tiene «si…» y cada paso tiene un solo sujeto y verbo.

Cada alternativo y cada excepción indica su paso de origen y cómo termina.

Hay postcondiciones para el éxito y para el fallo.

Taller práctico

Reserva de salas de estudio · Biblioteca Unilibre

Enunciado

Los estudiantes reservan salas de estudio por bloques de 2 horas desde el portal. Para reservar deben estar a paz y salvo con la biblioteca. Pueden cancelar hasta una hora antes. Si el grupo no llega en los primeros 15 minutos, el sistema libera la reserva automáticamente. Al llegar, el bibliotecario registra la entrega de la sala y, si la piden, de equipos (portátil o video beam). Cada reserva confirmada se notifica por correo institucional.

Entregables

1. Lista de 6 RF y 3 RNF verificables.

2. Diagrama con al menos un include, un extend y el actor Tiempo.

3. Especificación completa de Reservar sala y Cancelar reserva con la plantilla vista.
